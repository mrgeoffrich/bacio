A bacio dispatch has arrived. The work itself is substantive —
delegate it to a per-mode subagent so this conversation's context
stays at "dispatch arrived → Task call → summary → reply" size
rather than absorbing every file read, edit, and tool call the job
makes.

The dispatch stub below names the ticket, the mode, the resolved
base branch, and the custom subagent type to spawn, each as its own
XML-style tag. The durable per-mode brief is NOT in this payload —
it lives in that subagent's own system prompt
(`.claude/agents/bacio-<mode>-worker.md`, generated by
`bacio install-agent`).

Call:

    Task(
      subagent_type = <the value inside the <subagent_type>...</subagent_type> tag from the stub below>,
      prompt        = <the <issue_id>, <mode>, and <base_branch> tags from the stub
                       below — copied VERBATIM, with exactly one tag appended on
                       its own line: <dispatch_id>N</dispatch_id> where N is the
                       dispatch_id attribute of the <channel> tag.
                       Do NOT rephrase, summarise, or add anything else.>,
    )

The worker's `Task` prompt is a fixed four-tag stub —
`<issue_id>...</issue_id>`, `<mode>...</mode>`,
`<base_branch>...</base_branch>`, `<dispatch_id>...</dispatch_id>`
— and nothing else. Do not write a sentence describing the job;
the subagent's own system prompt (its agent file) is the single
source of truth for what to do. Your only job here is to copy the
`<issue_id>`, `<mode>`, and `<base_branch>` stub tags verbatim and
append the `<dispatch_id>` tag. The `<subagent_type>` stub tag is
your input for the `subagent_type` argument — it is not part of the
worker's prompt. An issue-less or pre-BACI-226 dispatch may omit
`<base_branch>` from the stub; in that case just omit it from the
Task prompt too (the worker falls back to `main`).

Do NOT set `model` on the Task call — the subagent's agent file
already pins it. Do NOT paste a brief — the subagent already has it.

If the Task call fails because the subagent type is unknown, the
consuming repo has not run `bacio install-agent` yet — surface that
as `needs_input: run bacio install-agent` and stop.

The subagent's system prompt is written from the worker's
perspective: it claims the ticket, does the work, releases the claim,
and calls mcp__bacio__reply. You don't follow those steps yourself —
the subagent does.

When Task returns, forward the subagent's one-line summary as your
visible response. If the subagent returns `needs_input: <what is
missing>` rather than completing the work, surface that line and
stop so the supervisor can answer. (The worker signals "waiting on
the user" by leaving an open `ask_user_question` on the ticket, not
by a state flip — there is no longer a `needs_action` state.)

After Task returns, call mcp__bacio__reply with the dispatch_id from
the <channel> tag to acknowledge the dispatch.

Caveat: a running subagent is NOT interruptible mid-flight.
Cancelling a dispatch in the UI clears the queue but does not stop
work already in progress.
