# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Required reading before planning or implementing

Two docs in `docs/` carry the non-obvious conventions this codebase relies on. Read whichever is relevant **before** you start planning a change — they'll shape the design, not just check it after the fact.

- **[`docs/agent-cli-principles.md`](docs/agent-cli-principles.md)** — the six rules every mutating CLI command honours (JSON in via `--json`, schema reachable via `bacio schema`, lean output by default, validation at the store boundary, `--dry-run` support, documented in `SKILL.md`) plus the explicit "deliberately don't do" list. Read before adding or changing any CLI command.
- **[`docs/tui-cookbook.md`](docs/tui-cookbook.md)** — bubbletea v1.3.10 + lipgloss v1.1.0 + bubbles patterns, pinned to v1. Upstream READMEs have moved to v2 and will mislead you. Read before any non-trivial work in `internal/tui/`.

The deeper context for both lives in the topic sections below (`## Agent-CLI principles` and `## TUI cookbook`).

## Quick commands

- **`./build.sh`** — **always run this before validating, testing, retesting, or smoke-testing anything.** Default is the full rebuild: the web bundle (embedded into the CLI binary at `/ui/`), the CLI/TUI binary (installs to `~/.local/bin/bacio`), the regenerated Wails bindings, the desktop frontend, and the desktop Go binary. The user's TUI + desktop + per-session `bacio channel` MCP processes all share the same SQLite store, so a schema change with a stale binary still running anywhere will surface as "no such column" errors. Opt-out flags for the inner loop: `--skip-web` (skip the Vite web bundle — saves the npm install + Vite step when nothing in `desktop/frontend/` changed) and `--skip-desktop` (skip the Wails desktop build). Combine them (`--skip-web --skip-desktop`) for CLI/TUI-only. Before asking the user to test, run this and tell them to restart any running TUI / desktop / agent sessions to pick up the new binary.
- `go build ./...` — build everything in the main module (does NOT cover `desktop/` — it's a separate nested module; use `./build.sh` instead).
- `go build -o ~/.local/bin/bacio ./cmd/bacio` — install just the CLI/TUI binary. Equivalent to the CLI step inside `./build.sh --skip-web --skip-desktop`.
- `go vet ./...` — vet the codebase.
- `go test ./...` — run the unit tests.
- `bacio <subcommand>` from inside any git working tree drives the CLI.
- The SQLite database lives at `~/.bacio/db.sqlite` by default. Override via `--db <path>` when testing or validating changes.
- **Smoke-testing a desktop / web change.** The same React tree drives both the Wails desktop binary and the web bundle, so the cheapest agent-driven validation is the web path: run `bacio api` (default `http://localhost:5320/ui/`) and drive the UI with the `playwright-cli` skill — no Wails native-window dance, and snapshots come back as readable accessibility trees. After a frontend change, `./build.sh --skip-desktop` is enough to refresh the embedded bundle; restart the running `bacio api` to pick up the new binary.

## Profiling

Three hidden persistent root flags capture profiles/traces — a dev/debug affordance, kept out of `--help`:

- `bacio --cpuprofile <path> tui` — writes a CPU profile covering the whole interactive session.
- `bacio --memprofile <path> tui` — writes a heap profile (`runtime.GC()` then `pprof.WriteHeapProfile`) of what survived the session.
- `bacio --trace <path> tui` — writes an execution trace covering the whole session. Unlike the CPU profile, the trace captures off-CPU events (goroutine scheduling, blocking on syscalls/channels/mutexes), so it's the tool for diagnosing UI freezes — a stall on a slow query or `git` shell-out is invisible to CPU profiling but shows up here.

They start in the root `PersistentPreRunE` and flush in `stopProfiling` (`internal/cli/profiling.go`). `NewRoot()` returns that cleanup func; `cmd/bacio/main.go` runs it after `Execute()` returns — on success and error alike — so profiles flush even when a command exits via an error path (cobra skips `PersistentPostRunE` on error). Open CPU/heap output with `go tool pprof <path>`, trace output with `go tool trace <path>`. Today the flags are wired for `bacio tui`; extending them to the short-lived CLI commands is a possible follow-up.

## Architecture in one screen

- Entry point: `cmd/bacio/main.go` → `internal/cli.NewRoot()` (cobra). `NewRoot()` returns `(*cobra.Command, func())` — the func is a cleanup closure `main.go` runs after `Execute()` to flush pprof profiles (see ## Profiling).
- CLI commands: `internal/cli/*.go`, one file per command group (`issue`, `feature`, `repo`, `doc`, `link`, `pr`, `tag`, `comment`, `history`, `status`, `init`, `install_skill`, `install_hooks`, `tui`, `agent`, `hook`, `channel`). Cross-cutting helpers live in `audit.go`, `context.go`, `output.go`, `output_flag.go`, `input.go`, `doc.go`.
- Agent supervision/dispatch: `internal/cli/hook.go` (the `bacio hook` Claude Code hook shim) and `internal/cli/channel.go` + `internal/channel/` (the `bacio channel` MCP-over-stdio server) keep the local agent registry in sync and deliver `agent_dispatches` work items to running sessions. Both are harness-integration shims — see ## Harness-integration shims.
- Persistence: `internal/store/` over SQLite (`modernc.org/sqlite`, pure-Go, no CGO). Schema is in `internal/store/schema.sql` and re-applied on every `Open` — adding a new table is a matter of appending another `CREATE TABLE IF NOT EXISTS …`. Schema changes that need real ALTERs go through `migrate()` in `internal/store/store.go`.
- Domain types: `internal/model/` — pure structs/enums, no DB.
- Git detection: `internal/git/detect.go` shells out to `git` for repo root + remote URL.
- TUI: `internal/tui/` — bubbletea v1.3.10 + lipgloss v1.1.0 + bubbles v0.21.0. Shell in `tui.go` owns the tab strip and routes keys; each tab implements the local `view` interface. Six tabs: Board, Features, Documents, Agents, History, Settings. The Settings tab (`settings.go`) is the only view with a raw-text editor — `bubbles/textarea` for prompt-template bodies; see the `CapturesInput()` note under ## Conventions.
- Desktop app: `desktop/` is a **separate nested Go module** (`github.com/mrgeoffrich/bacio/desktop`) driven by Wails v3 + React + Vite (TypeScript). It is invisible to `go build ./...` from the repo root — build it via `wails3 build` from inside `desktop/`. The durable reference is the `docs-wails-v3-react-research.md` bacio doc; v3 is alpha (pinned to `v3.0.0-alpha.90`) so don't trust hosted docs at `v3.wails.io` blindly.
  - **Two build modes (BACI-30).** The same React tree builds two ways. Default `wails3 build` / `npm run build` produces the native desktop binary that talks to Wails-bound Go services. `npm --prefix desktop/frontend run build:web` (or `./build.sh`, which builds the bundle by default — pass `--skip-web` to opt out) produces a browser bundle that talks to the existing `bacio api` HTTP server — copied to `webui/` at the repo root and embedded into the `bacio` binary at compile time (a second `//go:embed` in `embed.go`, same upward-traversal caveat as `SkillMarkdown`). `bacio api` serves it at `/ui/`. Vite's `--mode web` aliases `./api` → `./api.http.ts` (fetch + reshape onto REST) and `@wailsio/runtime` → a no-op stub so module-level imports don't crash a browser. Components read `WEB_MODE` from `desktop/frontend/src/env.ts` to branch behaviour where the desktop has a Wails-only affordance — Add Repository opens a path-input modal in web mode (POSTs to `POST /repos`) instead of the native folder picker, and leader-status comes from polling `GET /leader` instead of a Wails event subscription. BACI-50 closed the last four "hidden" surfaces (Agents tab via the composite `GET /repos/{p}/agents/cards`, typed prompt-template CRUD over REST, Add Repository modal, and the leader chip — `bacio api` now runs the elector itself alongside the desktop + TUI). The durable reference is `docs/web-app-mode.md` — read before extending or fixing web-mode behaviour. CORS is opt-in via `bacio api --cors-origin <url>` (repeatable, default empty = same-origin only).
  - **Data-refresh model.** `cards` and `agents` are App-owned state (`desktop/frontend/src/App.jsx`); `Board` and `AgentsView` are presentational and read them via props. App orchestrates freshness with three effects: an eager load on repo change, a refresh-on-switch when `activeView` becomes `board`/`agents`, and a `POLL_INTERVAL_MS` (10s) `setInterval` poll that runs only while on those two screens. `FeaturesView`/`DocsView`/`HistoryView` are self-owning — App renders one view at a time, so they re-fetch via their own mount effect on remount. A future change that keeps all views mounted (CSS display-toggle instead of the unmounting ternary) would break refresh-on-switch for the self-owning views. `hideEmptyColumns` (the Board preference) is also App-owned: loaded from `app_settings` in the mount effect alongside `columns`/`promptConfig`, flipped live from the Settings screen, and passed to the presentational `Board` as a prop.
  - **`BoardCard.Taken`.** `BoardCard` carries a derived `Taken` flag, set in `BoardService.ListCards` from the new `client.ListOpenClaims` method (one bulk query per board, keyed by issue key). A taken card renders bold with an accent border and has its drag + per-card action button disabled — a UI-level guard against a human stepping on in-flight agent work, not a hard lock.
  - **`BoardCard.WaitingForClaim`.** `BoardCard` also carries `WaitingForClaim`, copied straight off `model.Issue.WaitingForClaim` in `cardFromIssue` (no extra query — it's a stored issue column, unlike `Taken`). A waiting card replaces its per-card action button with a CSS spinner (`.mk-card-spinner`) and disables drag; `Taken` takes precedence if both are set. See the `issues.waiting_for_claim` convention note below.
  - **Error handling (BACI-43).** Unexpected failures — Wails binding rejections, thrown exceptions, render-time crashes — surface through a single global modal. Call sites push via `reportError(err, { headline: '…' })` from `desktop/frontend/src/errors.ts`; the `<ErrorModal>` mounted at the bottom of `App.jsx` subscribes to the bus and renders one error at a time (FIFO, with same-headline+message coalescing inside a 2s window so a flapping poll shows as "Couldn't refresh board (×7)" instead of 7 modals). Each top-level view (Board, AgentsView, FeaturesView, DocsView, HistoryView, SettingsView) and the IssueDrawer / IssueEditModal / CommandPalette overlays are wrapped in `<ErrorBoundary>` so a render-time throw replaces that subtree with a "Reload this view" fallback and reports — the Topbar and other views stay alive. The bus is a module-level singleton so non-React callers reach it too: `installGlobalErrorHandlers()` (called once from `main.tsx`) wires `window.error` + `unhandledrejection`, and `ErrorBoundary.componentDidCatch` forwards as well. Background heartbeats (`refreshCards`/`refreshAgents` poll-loop with `opts.silent`, the initial `getLeaderStatus`, and `refreshPromptConfig`) stay silent — they `console.warn` only — to avoid modal-spamming a flapping connection. Reuses the existing `.mk-modal-backdrop`/`.mk-modal` CSS; the error variant adds a `--status-blocked` accent border + tinted title so it reads as an error not a confirmation. Stack/`detail` is shown only under `import.meta.env.DEV`.

## Agent-CLI principles (read before planning a feature)

`docs/agent-cli-principles.md` is the durable reference for the conventions bacio adopted from Justin Poehnelt's "Rewrite Your CLI for AI Agents". Every mutating command accepts JSON via `--json`, publishes its schema via `bacio schema`, returns lean output by default, validates input at the store boundary, supports `--dry-run`, and is documented in `SKILL.md`. New CLI work should honour those six rules and the explicit "deliberately don't do" list (no NDJSON, no `--field` projection, no silent input normalisation, etc.).

The exception is **harness-integration shims** (see below): `bacio tui`, `bacio api`, `bacio hook`, `bacio channel`. These aren't agent-facing mutation commands — they're glue to a host (a terminal, an HTTP client, the Claude Code hook/channel runtime) — so they deliberately skip the six rules (no `--json`, no `bacio schema` entry, no `--dry-run`). They're still documented in `SKILL.md`. Agent-facing dispatch verbs (`bacio agent dispatch` / `ack`) DO follow the six rules.

## Harness-integration shims

`bacio hook` and `bacio channel` integrate bacio with the Claude Code agent runtime; they keep the local agent registry (`agents` / `agent_sessions` / `agent_claims` / `agent_dispatches`) in sync without the agent calling `bacio agent …` by hand.

- **All five hook subcommands AND the channel's setup-dispatch poller are gated on `BACIO_AGENT_MODE` (BACI-48).** `internal/agentmode.Enabled()` is the single source of truth: it reads `BACIO_AGENT_MODE` and accepts only `"1"` or `"true"` as enable signals (case-sensitive, restrictive on purpose so the gate is binary and visible). When unset, each hook subcommand logs a one-line `bacio hook <event>: BACIO_AGENT_MODE not set — skipping` to stderr and exits 0 without touching the DB; the channel still completes the MCP handshake and keeps `register` / `reply` reachable but skips starting the setup-dispatch poller (so no register-nudge is queued and no drain runs). Rationale: a user running `claude` interactively in a bacio-tracked project should not be silently minted an agent identity. `BACIO_AGENT_MODE=1` is the explicit opt-in for agent sessions. `bacio status` surfaces the current value (text + JSON) under an `Agent:` / `agent_mode` field; the install banners on `bacio install-hooks` / `install-channel` print the recommended launch command (`BACIO_AGENT_MODE=1 claude --dangerously-skip-permissions --dangerously-load-development-channels server:bacio` — BACI-49) on stderr. The activation banner helper lives in `internal/cli/install_common.go`; the gate helper for hooks is `skipUnlessAgentMode(subcommand)` at the top of each hook subcommand's `RunE`, the channel's gate is the `agentmode.Enabled()` check that picks `srv.ServeMCP` (read-loop only) vs `srv.Run` (read-loop + poller) in `internal/cli/channel.go`. The split in `internal/channel/channel.go` keeps `Run` for back-compat (existing tests) and exposes `ServeMCP` for the "transport up, poller parked" case.
- **`bacio hook <event>`** (`internal/cli/hook.go`) — hidden command group. Each subcommand (`session-start`, `user-prompt-submit`, `stop`, `session-end`, `post-tool-use`) reads a Claude Code hook-event JSON payload on stdin, correlates by `session_id`, and either creates a minimal session stub (`session-start` only — see below), heartbeats it, ends it, or mirrors its TodoWrite list (`post-tool-use` — see the BACI-45 convention bullet below). Hard rule: a hook handler must NEVER fail the agent's session — every path returns nil (exit 0); problems go to stderr. `bacio install-hooks` merges these into a repo's `.claude/settings.json` (non-destructive merge — see ## `bacio install-skill`). **SessionStart is now deliberately thin**: it calls `CreateSessionStub` to insert just `session_id + repo + claude_pid + host` (placeholder actor `"unregistered"`, `registered_at` NULL). All the enrichment — agent identity mint, `agents.json` write, model/branch/permission_mode/channel_version — happens later in the bacio channel's `register` tool. This kills the SQLite-write-contention race that used to lose identity mints under the old "do everything at SessionStart" hook, and the registered-only UI filter (default in TUI/desktop/CLI; opt out with `bacio agent list --all`) hides sessions that never made it through `register`.
- **`bacio channel`** (`internal/cli/channel.go` + `internal/channel/`) — hidden command. A pure-Go MCP server over stdio implementing Claude Code's "channel" contract. **Scoping by `(host, claude_pid)`, not agent identity**: every tick the channel calls `Source.EnsureSetup`, which queries `SessionsByClaudePID(host, claude_pid)`, filters to sessions where `registered_at IS NULL`, and idempotently queues a `created_by="bacio-channel"` setup dispatch *targeting the session_id directly* (synthetic `notifications/claude/channel` events without a real `dispatch_id` aren't surfaced to the agent by Claude Code, so the setup nudge goes through the proven dispatch path). `Source.Drain` walks the same sessions and drains each via `DrainDispatches(session_id)`. The setup-dispatch payload is rendered per-session with the real `session_id` pre-substituted into the JSON example (BACI-46) — copy-pasting it verbatim yields a valid `register` call rather than the literal `$CLAUDE_CODE_SESSION_ID` placeholder; the validator (`store.ValidateSessionID`) is the belt-and-braces guard, refusing obvious placeholder strings (anything starting with `$`, the bare token, template-bracket shapes) with an actionable error. The `register` tool (the agent's first turn) accepts `session_id` plus optional `model`, `branch`, `permission_mode`, `mcp_version`, and calls `CompleteRegistration` — which resolves/mints identity, writes `.bacio/agents.json`, enriches the session row, stamps `registered_at`, and links `channel_seen_at` via `LinkSessionChannel`. `serverInfo.version` reports the real bacio binary version (via `internal/version.Version`); the agent echoes it back as `mcp_version` so `bacio agent list` can flag stale channel processes still running after a binary upgrade (`MCP` column with a `!stale` annotation). `internal/channel/` is the wire protocol (newline-delimited JSON-RPC 2.0), decoupled from the store via the `channel.Source` interface (`Drain` / `Ack` / `Heartbeat` / `Register` / `EnsureSetup`). Must never hard-fail: an idle channel is better than a failed one. `Server.Run` waits for the poller before returning so the caller's `defer c.Close()` can't race an in-flight `Drain`. Channels are a Claude Code research preview — a custom channel needs `--dangerously-load-development-channels`; caveats live in the command's `Long` help. `bacio install-channel` (`internal/cli/install_channel.go`) registers the `bacio` server in `<git-root>/.mcp.json` (non-destructive merge, same `--yes`/confirm-prompt behaviour as `install-hooks`) and prints the launch command.
- The **pull** path (hooks draining dispatches on prompt) and the **push** path (the channel) are independent — an agent can use either or both. `DrainDispatches` on the `client.Client` interface is the shared primitive.

## Conventions that aren't obvious

- **`recordOp` after every mutation.** Every CLI command that writes to the database calls `recordOp(s, model.HistoryEntry{...})` from `internal/cli/audit.go`. History prune failures and audit-write failures log to stderr but never fail the user-visible command. New mutating commands MUST follow this pattern.
- **Repos auto-register.** `resolveRepo()` in `internal/cli/context.go` creates a `repos` row on first use from inside a git working tree. There's intentionally no separate `bacio repo init`.
- **Actor (`--user`).** Every history row is stamped with an actor name. The default is the OS user; AI agents are expected to pass `--user <name>` explicitly so audits attribute work correctly. Plumbing lives in `audit.go`.
- **TUI view contract.** Each tab in `internal/tui/` is a struct implementing pointer-receiver `Update(msg tea.Msg) tea.Cmd`, `View(width, height int) string`, `Help() string`, `HasOverlay() bool`, `CloseOverlay()`, `Status() string`, `Breadcrumb() string`, and `CapturesInput() bool`. When `HasOverlay()` returns true the shell stops intercepting `esc` / digit / `tab`, so the overlay's own `esc` closes it instead of quitting the program. **`CapturesInput()` is the raw-input-capture contract:** a view returns true only while it is focused on a raw text input (e.g. a `bubbles/textarea`), and while true the shell yields `q` and the digit keys to the view so they can be typed literally rather than quitting / switching tabs. `ctrl+c` is never yielded — it is always a hard quit. Any future text-editing view (e.g. an "edit description" overlay) must implement `CapturesInput()` the same way; views with no text input return false unconditionally.
- **Per-repo TUI state.** Generic key-value table `tui_settings(repo_id, key, value)` lives in `schema.sql`; helpers in `internal/store/tui_settings.go`. Used today for hidden columns; reuse for any future TUI preference instead of adding a typed table.
- **Global app settings.** `app_settings(key, value, updated_at)` is the global (not per-repo) sibling of `tui_settings`; helpers in `internal/store/app_settings.go`. Used today for the desktop Board's `board.hide_empty_columns` preference (auto-hide kanban columns with zero cards), edited from the desktop Settings screen via `client.Get/SetBoardPreferences`. Like the agent registry, `app_settings` has no remote analogue in v1 — the `remoteClient` methods return `ErrLocalOnly`. Reuse `app_settings` for any future *scalar* global preference rather than adding a typed table.
- **Dispatch prompt templates** live in their own `prompt_templates(slug, name, body, allowed_states_json, is_builtin, …)` table (`internal/store/prompt_templates.go`), not in `app_settings`. The table is seeded from the embedded `internal/model/prompttemplates/<slug>.txt` files on first run (`migratePromptTemplates`), then the user owns every row — they can edit body/state-gate, rename, delete, restore deleted built-ins (idempotent via `RestoreBuiltinPromptTemplates`), and add their own templates. The three editing surfaces are the desktop Settings screen, the TUI Settings tab (`internal/tui/settings.go`), and `bacio settings template ...` (`internal/cli/settings.go`). The TUI Settings tab talks to the store directly and records its own audit rows via `recordTUIOp`, mirroring the `template.create` / `delete` / `rename` / `restore_defaults` ops + the existing `prompt_template.update`/`reset` and `prompt_states.update`/`reset` op names the `localClient` writes. `app_settings` keeps the legacy `Set/GetPromptTemplate(s)` shims for back-compat; new code should call the typed `Store.ListPromptTemplates` / `AddPromptTemplate` / etc. directly.
- **Template slugs outlive templates.** `agent_dispatches.mode` is a free-form text slug, validated only for shape (`model.ParseDispatchMode` is now a slug-shape check, not an enum membership check). A *renamed* template's old dispatch rows are cascade-updated to the new slug inside the rename transaction. A *deleted* template's historical dispatches keep the slug verbatim — renderers should treat an unrecognised slug as "removed", not error out.
- **State-gated dispatch + auto-pick.** The desktop per-card action button and the TUI dispatch picker only offer a template when the card's state is in that template's `allowed_states` (built-in defaults: `model.DefaultPromptStatesForBuiltinSlug(slug)`). `BoardService.DispatchIssue` re-checks the gate and **enqueues** a target-less dispatch (status `queued`); it takes no agent argument. The issue drawer has no agent-selection UI.
- **Dispatch queue + matcher (BACI-51).** Auto-pick dispatches (the desktop per-card button, TUI `x`, REST `POST .../dispatch`, CLI `bacio agent dispatch <key> --mode <stage>` with no `--to`/`--session`) **always succeed** as `queued` — the "no free agent" error is gone. A background **matcher** in `internal/dispatcher/` ticks ~every 5s (`store.QueueMatchInterval`) on whichever process holds `ui_leader`, walks each `(repo, mode)` queue oldest-first, and binds the head of the FIFO to a free agent (`status: queued → pending`, stamps `target_agent_id`) inside a single `store.BindQueuedDispatch` transaction. The picker (`internal/dispatcher/picker.go::AutoPickFreeAgent`) is the same shape the pre-BACI-51 client used; it lives in `dispatcher` so the matcher and any future callers can share it without circular imports. Matcher binds **write no audit row** — mechanical janitor work, matches the prune precedent. Each `prompt_templates.concurrency_limit` row caps the per-(repo, mode) in-flight count (`pending + delivered`, excluding `created_by = bacio-channel` setup rows). `0` = unlimited; built-in `ship` seeds to `1` so merges serialise (`model.DefaultConcurrencyLimit`). Targeted dispatch (`--to <agent>` and/or `--session <id>`) bypasses the queue and goes straight to `pending` via `CreateDispatch`. The CHECK relax + `concurrency_limit` ALTER are gated migrations (`store.migrateAgentDispatchesStatusCheck` + the `columnExists` check), keyed off the stored `CREATE TABLE` SQL so re-runs are no-ops. The spinner that `waiting_for_claim` triggers is now also a **clickable cancel** in the desktop (`BoardService.CancelWaitingDispatch` → `client.WaitingDispatchForIssue` + `client.CancelDispatch`), web mode (REST `GET /repos/.../waiting-dispatch` + `POST /agents/dispatches/{id}/cancel`), and TUI (`X` keybind on a waiting card). The per-template concurrency cap is editable from the desktop Settings panel and via `bacio settings template set-concurrency <slug> <n>`; the TUI Settings tab editor is a noted follow-up.
- **History retention.** `HistoryRetention` in `internal/store/store.go` is 60 days. `pruneHistory` runs on every `Open`. Adjust there if needed. `AgentSessionRetention` and `AgentDispatchRetention` mirror it (60 days, ended/settled rows only) — `pruneAgentSessions` / `pruneDispatches` also run on every `Open`.
- **Live-list agent-session prune.** In addition to the 60-day `pruneAgentSessions` that runs on every `store.Open()`, the controlling UI (whichever process currently holds `ui_leader`) runs a 5-minute ticker (`store.UILeaderPruneInterval`) that calls `Store.PruneEndedAgentSessions(store.AgentSessionLiveListRetention)` (4h). Keeps the live "Agents" lists tidy without a UI-side filter. `agent_claims` rows cascade away via the FK; `agent_dispatches` survive (cleaned by the existing 60-day `pruneDispatches`). No audit row per tick — mechanical janitor work stays out of `bacio history`, matching the other prune passes. Trigger lives in each UI's loop (TUI: `pruneTickMsg` in `internal/tui/tui.go`; desktop: a second goroutine in `LeaderService.ServiceStartup` in `desktop/leaderservice.go`; `bacio api`: a second goroutine in `newAPILeaderService` in `internal/api/leaderservice.go`).
- **Claims carry a `prompt`; `taken`/`busy` are derived, never stored.** `agent_claims` has a `prompt` column (the instruction the agent claimed from). An issue is `taken` and a session is `busy` iff there's an open (unreleased) claim — `model.SessionBusy` and the `taken` field in issue views compute this; the claim rows are the single source of truth, so nothing can drift. Reuse `agent_claims` (and `store.ListClaimsForIssue` / `OpenClaimsBySession`) for per-issue session history rather than a parallel table. Both UIs surface `taken` as a guard against accidental human interference: the desktop Board bolds a taken card and disables its drag + per-card action button, and the TUI board renders a taken card bold with amber key brackets and refuses the `x` dispatch on it.
- **Claiming keeps `issues.assignee` in lockstep with the claim.** `taken` is derived from claim rows, but `assignee` is a stored column — and `store.AddAgentClaim` / `ReleaseAgentClaim` / `EndAgentSession` keep the two aligned by writing `issues.assignee` inside the *same* transaction as the claim mutation. A fresh claim stamps the assignee with the claiming identity (last claim wins, even over a human-set value); releasing the last open claim clears it again, but only if the assignee still equals the releasing identity (a human's deliberate reassignment is preserved). The store methods return a `store.AssigneeChange` (or `[]AssigneeChange` for `EndAgentSession`) so the client layer can record the matching `issue.assign` audit row alongside `agent.claim` / `agent.release` / `agent.end`. New claim/release/end paths MUST go through these helpers (`sessionIdentity`, `applyClaimAssignee`, `clearAssigneeIfOwned`) rather than touching `issues.assignee` separately.
- **`issues.waiting_for_claim` is the *opposite* kind of signal — a real stored column, not derived.** Where `taken` is computed from claim rows, `waiting_for_claim` is a genuine `INTEGER` column on `issues` (BACI-26). It's the "a dispatch is queued but no agent has claimed yet" gap-state: `store.AddDispatch` sets it to `1` (transactionally, when the dispatch targets an issue), and `store.AddAgentClaim` (new-claim path) / `store.CancelDispatch` clear it back to `0`. It can't be derived because a dispatch may target an agent identity with no live session and no claim row to compute from. It is **ephemeral runtime state**: deliberately **not** `updated_at`-bumping (so git-backed sync doesn't churn on every dispatch/claim) and **not** synced. Both UIs render a spinner on a waiting card and refuse dispatch on it; `taken` takes render precedence if (defensively) both are ever set. Toggle it via `store.SetWaitingForClaim`. Known gap: an abandoned dispatch (agent never claims, never cancels) leaves the flag stuck — a documented follow-up.
- **Agent TodoWrite mirror (BACI-45).** A fifth `bacio hook` event — `post-tool-use`, scoped via the settings.json `matcher: "TodoWrite"` — mirrors each session's TodoWrite list into the `agent_session_todos(session_pk, position, content, status, updated_at)` table. The mirror is **wholesale replace per write**, run inside a single transaction in `store.ReplaceSessionTodos` (DELETE then INSERT), so a partial write never shows a frankenlist. Validation lives in `store.ValidateSessionTodos` and enforces a 200-row cap (`model.MaxSessionTodos`), 1 KiB per content row, the canonical `pending|in_progress|completed` status vocabulary, and the multi-line control-char gate. The cap rejects the whole batch rather than truncating — a partial mirror would suggest "this is the agent's plan" when actually it's a clipped subset. Rows cascade away with the parent `agent_sessions` row via `ON DELETE CASCADE`, so the existing live-list / 60-day session prune sweeps them too — no separate retention pass. Bulk read via `store.ListTodosBySessions` keys results by session PK, mirroring `OpenClaimsBySession`, so the TUI Agents view (`internal/tui/agents.go`) and the shared `internal/agentcards.Assemble` (called by desktop `BoardService.ListAgents` and by the BACI-50 REST endpoints `GET /repos/{p}/agents/cards` / `GET /agents/cards`) hydrate every card on the 10s poll in one query. Both UIs render an `n/m done` badge on the card header and a glyph list (`○` pending, `◐` in_progress, `●` completed) in the per-agent drill-down. The REST surface is read-only at `GET /agents/sessions/{session_id}/todos`; writes are hook-driven only. **No `recordOp` per TodoWrite** — high-frequency tool calls would flood `bacio history` the same way heartbeats would. Local-only, like the rest of the agent registry; `remoteClient` returns `ErrLocalOnly`. The post-tool-use hook deliberately skips the `loadHookContext()` git-detect + repo-ensure dance because the FK is to `agent_sessions`, not repos — less startup latency on a high-frequency hook, no spurious "not in a git repo" stderr noise.
- **Claimed-issue state tracks agent idle/active automatically (BACI-14).** The Claude Code `Stop` hook is the precise "agent's turn ended, parked waiting on the user" signal — semantically a word-for-word match for `model.StateNeedsAction` — so the `bacio hook stop` handler walks every open claim the session holds and flips any `in_progress` issue to `needs_action`. The `bacio hook user-prompt-submit` handler is the symmetric inverse: a fresh prompt arrives and any `needs_action` claimed issue flips back to `in_progress`. The flip is **edge-only** — only issues already in the matching "from" state are touched, so a no-op turn writes nothing (no `SetIssueState` call, no audit row, no `updated_at` bump). Implementation: `hookContext.syncClaimedIssueStates(sessionID, idle bool)` in `internal/cli/hook.go`. The derived "session is parked" signal is `model.SessionWaiting(openClaims, needsActionKeys)` — mirrors `SessionBusy`; the TUI Agents view (`internal/tui/agents.go`) and desktop Agents view (`AgentCard.Waiting`/`WaitingIssue` in `desktop/boardservice.go`) render a `waiting · BACI-NN` badge in place of the busy badge when this fires. Cost is purely cosmetic (every turn on a claimed issue bumps `updated_at`, which feeds sync last-writer-wins) — a quieter audit path is a noted follow-up.
- **UI leader election (`ui_leader` table).** A single-row lease that surfaces a "Controlling" indicator on the one UI process currently holding it — both UIs can dispatch regardless of leader state. (Historically the lease gated automated dispatch; that gate was removed because it surprised users who couldn't action issues from a standby UI. The race it protected against — two UIs auto-picking the same free agent — is now considered tolerable.) Seeded in `schema.sql` with `heartbeat_at = 0`. The election is two conditional UPDATEs: ACQUIRE (succeeds only when `heartbeat_at < datetime('now', '-180 seconds')`) and RENEW (succeeds only when `holder_token` still matches). Because SQLite serialises writes, the CAS is atomic — exactly one process wins a race to ACQUIRE. Each process uses a **per-process UUIDv7 token** (never the PID) as the CAS key: the token, not staleness, gates RENEW, so a process that resumes after a laptop sleep re-takes its lease if nobody took over, and demotes to standby if they did. DB clock only (`datetime('now')`) — never the process clock. Timings: heartbeat every ~10s (`store.UILeaderHeartbeatInterval`), stale threshold 180s (`store.UILeaderStaleSeconds`). On graceful shutdown, best-effort `SET heartbeat_at = 0` so a standby promotes within one tick (~10s) instead of waiting 3 min. To widen what counts as "graceful", both UIs install a signal handler that converts SIGTERM/SIGHUP (TUI) and SIGINT/SIGTERM/SIGHUP (desktop) into the normal quit path so the deferred `Release` still fires — SIGINT is omitted in the TUI because bubbletea already turns it into a graceful quit. SIGKILL / power loss still fall through to the 180s stale window (irreducible). Raw helpers live in `internal/store/leader.go`; the shared loop logic lives in `internal/leader/leader.go` (`Elector.Tick()`). The TUI shell (`internal/tui/tui.go`) runs a `leaderTick` timer; the desktop's `LeaderService` (`desktop/leaderservice.go`) uses Wails `ServiceStartup`/`ServiceShutdown`; `bacio api` runs the same elector inside `Server.Run` (`internal/api/leaderservice.go`, exposed at `GET /leader`) so a browser pointed at the api sees the same chip the desktop does. Each UI renders a "Controlling" chip only when it holds the lease and nothing otherwise — there's no "Standby" affordance, since standby is the default. The `ui_leader` row is permanent (never deleted); no prune function is needed. The elector also gates a separate 5-minute prune ticker (`UILeaderPruneInterval`) that drops ended `agent_sessions` rows older than `AgentSessionLiveListRetention` — see the *Live-list agent-session prune* bullet above; the `Elector` itself stays minimal and just exposes `CurrentState().AmLeader` for the prune trigger to consult.

## `bacio install-skill` and `embed.go`

- `embed.go` lives at the module root because `//go:embed` cannot traverse upward; it embeds `.claude/skills/bacio/SKILL.md` into `embed.SkillMarkdown`. It also embeds `webui/` (the BACI-30 web-app bundle) into `embed.WebUIFS`; `internal/api/static.go` serves it at `/ui/`. The `webui/.gitkeep` anchor keeps the embed directive valid on a clean checkout, and `.gitignore` skips everything else under `webui/` so the built bundle never ends up in git.
- `bacio install-skill` writes that markdown to `<git-root>/.claude/skills/bacio/SKILL.md`, overwriting on every run so doc updates land in any repo that re-runs the command.
- `bacio install-hooks` (`internal/cli/install_hooks.go`) is the sibling for hooks: it *merges* bacio's command hooks into `<git-root>/.claude/settings.json` rather than overwriting — existing hooks for other events, and any non-bacio hooks on bacio's events, are preserved. Re-running replaces bacio's own hook groups in place (matched by the `bacio hook ` command marker), so it's idempotent. The hook block is defined inline in Go (`bacioHookEvents`) — each row carries `{Event, Subcommand, Matcher}` so the table supports both the four matcher-free hooks and the BACI-45 PostToolUse entry (matcher `TodoWrite`). The hook config is not embedded — it's config, not a doc. It prints a plan and prompts for confirmation before writing; `--yes`/`-y` skips the prompt (and `confirmPrompt` there is shared with `install-channel`).
- `bacio install-channel` (`internal/cli/install_channel.go`) is the same pattern for the channel MCP server: a non-destructive merge of a `bacio` entry into `<git-root>/.mcp.json` (other `mcpServers` and top-level keys preserved), confirm-prompt + `--yes`, then `printActivationBanner` prints the shared recommended launch command (`BACIO_AGENT_MODE=1 claude --dangerously-skip-permissions --dangerously-load-development-channels server:bacio` — BACI-49). The entry's `command` is the absolute path of the running binary (`os.Executable()`), so it resolves regardless of the MCP subsystem's PATH.
- `SKILL.md` is the canonical CLI reference for AI agents — keep it in sync when adding or changing commands.
