A bacio dispatch has arrived. The work itself is substantive —
delegate it to a per-mode subagent so this conversation's context
stays at "dispatch arrived → Task call → summary → reply" size
rather than absorbing every file read, edit, and tool call the job
makes.

The dispatch stub below names the ticket, the mode, and the custom
subagent type to spawn. The durable per-mode brief is NOT in this
payload — it lives in that subagent's own system prompt
(`.claude/agents/bacio-<mode>-worker.md`, generated by
`bacio install-agent`).

Call:

    Task(
      subagent_type = <the "Subagent:" value from the stub below>,
      prompt        = <the stub block below — the "Ticket:" and "Mode:"
                       lines — copied VERBATIM, with exactly one line
                       appended: "Dispatch ID: <n>" where <n> is the
                       dispatch_id attribute of the <channel> tag.
                       Do NOT rephrase, summarise, or add anything else.>,
    )

The worker's `Task` prompt is a fixed three-line stub — `Ticket:`,
`Mode:`, `Dispatch ID:` — and nothing else. Do not write a sentence
describing the job; the subagent's own system prompt (its agent file)
is the single source of truth for what to do. Your only job here is to
copy the `Ticket:` and `Mode:` stub lines verbatim and append the
`Dispatch ID:` line. The `Subagent:` stub line is your input for the
`subagent_type` argument — it is not part of the worker's prompt.

Do NOT set `model` on the Task call — the subagent's agent file
already pins it. Do NOT paste a brief — the subagent already has it.

If the Task call fails because the subagent type is unknown, the
consuming repo has not run `bacio install-agent` yet — surface that
as `needs_input: run bacio install-agent` and stop.

The subagent's system prompt is written from the worker's
perspective: it claims the ticket, does the work, releases the claim,
and calls mcp__bacio__reply. You don't follow those steps yourself —
the subagent does.

When Task returns, forward the subagent's one-line summary as your
visible response. If the subagent returns `needs_input: <what is
missing>` rather than completing the work, surface that line and
stop — your `Stop` hook will flip the still-claimed issue from
`in_progress` to `needs_action` automatically so the supervisor
can answer.

After Task returns, attach the subagent's transcript to the ticket
for traceability — call:

    mcp__bacio__attach_transcript(
      issue_key = <the "Ticket:" value from the stub below>,
      agent_id  = <the agentId from the Task result>,
      note      = <the subagent's one-line summary>,
    )

The Task result carries an `agentId` alongside the summary; pass it
verbatim. If the call fails (e.g. a harness too old to persist
subagent transcripts), note it and carry on — it is not fatal to the
dispatch. Then call mcp__bacio__reply with the dispatch_id from the
<channel> tag to acknowledge the dispatch.

Caveat: a running subagent is NOT interruptible mid-flight.
Cancelling a dispatch in the UI clears the queue but does not stop
work already in progress.
